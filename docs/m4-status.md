## 결과의 한계

최초 기준 실행은 답변 `m2-v2`, 초안 `ticket-draft-v1`입니다. 이후 사용자가 v2 컨테이너를 적용했고 실제 회귀를 확인했습니다. 앱의 Docker 직접 접근 제한과 최초 요청 지연 이슈는 해결됐다고 단정하지 않습니다. 프롬프트 수정만으로 근거 충실도가 보장되지는 않습니다.

질문은 같은 합성 매뉴얼 2개를 바탕으로 개발 Agent가 만든 소규모 자료입니다. 외부 독립 평가가 아닙니다. 첫 관측 이후 수정에 참고했으므로 같은 질문을 다시 실행하면 회귀 평가로 분류합니다. 별도 미사용 평가셋은 남아 있습니다.

관측 시간은 최초 요청 약 29.2초, 이후 요청 약 2.3~3.5초였습니다. 서버 캐시·부하를 통제하지 않았고 답변/초안이 섞인 8건이므로 cold/warm 성능이나 p95 목표 달성으로 해석하지 않습니다. 토큰 비용과 메모리 측정도 남아 있습니다.

## 다음 재개 순서

**아래 1~3번은 완료한 v2 회귀 절차입니다. 현재는 위 최신 재개 지점의 읽기 전용 자원 진단부터 진행합니다.**

1. 사용자 PowerShell의 프로젝트 루트에서 새 AI 이미지를 적용합니다. 기존 DB·모델 volume을 유지합니다.

   ```powershell
   docker compose -f compose.yaml -f compose.m2.yaml -f compose.m3-app.yaml --profile rag up -d --build --wait --wait-timeout 300 ai
   ```

2. Healthy 확인 후 아래 평가를 한 번 실행합니다. 실제 LLM 비용이 발생하며 API 요청은 최대 8건입니다. 티켓을 생성하지 않습니다.

   ```powershell
   uv run --no-sync python scripts/evaluate_m4.py --execute
   ```

3. 새 결과의 초안 `prompt_version=ticket-draft-v2`를 확인하고 8건의 계약·문장 근거를 다시 검토합니다. 원본 v1 결과를 덮어쓰지 않습니다. 평가기가 생성한 Markdown은 사람 검토용 빈 양식이며 PASS를 의미하지 않습니다.
4. 미사용 질문으로 최종 품질 확인 → 장애/복구 검사 → 지연·메모리 측정 → 재현 안내·시연 자료 정리 순서로 진행합니다.
