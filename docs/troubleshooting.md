## TS-001 — Docker가 설치되어 있어도 서비스는 실행되지 않음

- 증상: Docker 버전 명령에서 클라이언트는 표시되지만 엔진 파이프를 찾을 수 없었습니다. 제한된 실행 환경에서는 Docker 설정 파일 접근도 거절되었습니다.
- 확인: 접근 권한을 확보한 상태에서도 desktop-linux 엔진 연결이 실패했으므로, 단순한 권한 문제와 엔진 중지 상태를 구분했습니다.
- 조치: 설치된 Docker Desktop을 시작하고 엔진 응답을 확인한 뒤 컨테이너 작업을 수행했습니다.
- 검증: Docker 29.2.1 서버 응답, PostgreSQL Testcontainers 기동, Compose 4개 서비스 healthy 확인.
- 재발 방지: 실행 안내에 Docker Desktop의 Linux 엔진이 실행되어 있어야 한다고 명시했습니다.
- 관련 자료: [실행 안내](runbook.md), [Compose](../compose.yaml).

## TS-002 — Maven 버전 설정 인자가 잘못 전달됨

- 증상: wrapper 생성 과정에서 `Unknown lifecycle phase ".9.11"` 오류가 발생했습니다.
- 원인: PowerShell의 네이티브 명령 인자 처리 과정에서 따옴표 없는 `-Dmaven=3.9.11`이 의도대로 전달되지 않았습니다.
- 조치: 전체 시스템 속성 인자를 따옴표로 감싸 `'-Dmaven=3.9.11'`, `'-Dtype=only-script'`로 전달했습니다.
- 검증: 공식 wrapper 3.3.4가 Maven 3.9.11 URL로 생성되었고 BUILD SUCCESS를 확인했습니다. 이후 Windows wrapper로 JUnit 및 PostgreSQL 통합 검증을 수행했습니다.
- 재발 방지: 점·공백·경로가 포함된 네이티브 인자를 하나의 인자로 전달합니다. wrapper 스크립트를 임의로 흉내 내서 작성하지 않습니다.
- 관련 파일: [wrapper 설정](../business-service/.mvn/wrapper/maven-wrapper.properties).

## TS-003 — 빌드 준비가 사용하지 않는 플러그인 의존성까지 내려받음

- 증상: Dockerfile의 `mvn dependency:go-offline` 단계에서 애플리케이션과 직접 관계없는 대량의 플러그인/클라우드 BOM 조회가 이어졌습니다.
- 확인: 로그에서 실제 애플리케이션 컴파일 전에 Flyway 플러그인 관련 광범위한 의존성 탐색이 진행되는 것을 확인했습니다.
- 조치: 해당 준비 단계를 제거하고 실제 `mvn -B -ntp package`를 실행하도록 변경했습니다. BuildKit cache mount로 Maven 저장소를 재사용합니다.
- 검증: 컨테이너 빌드와 내부 Java 테스트가 통과하고 Business 서비스가 healthy가 되었습니다.
- 한계: 같은 조건에서 전후 시간을 정식 벤치마크하지 않았으므로 “몇 배 빨라졌다”는 성능 수치는 주장하지 않습니다.
- 관련 파일: [Business Dockerfile](../business-service/Dockerfile).

## TS-004 — 화면 테스트의 기본 3초 제한 초과

- 증상: Python API 테스트 16건은 통과했지만 Streamlit AppTest 첫 실행에서 `AppTest script run timed out after 3(s)`로 실패했습니다.
- 확인: 실패 위치는 화면 초기 실행 대기였습니다. 네트워크 조회 함수는 테스트에서 대체되어 있었으므로 실제 API 지연을 측정한 실패는 아닙니다. 첫 import 및 당시 장비 부하의 세부 기여도는 분리 측정하지 않았습니다.
- 조치: UI 테스트 초기 실행 제한을 명시적으로 30초로 설정했습니다. 테스트의 결과·표·기간 assertion은 그대로 유지했습니다.
- 검증: 단독 UI 테스트 1건 통과, 이후 전체 pytest 17건 통과. 화면이 API 응답의 INC-014를 표시하고 종료일을 다음 날 00:00의 배타 경계로 전달하는 것도 검증했습니다.
- 재발 방지: 화면 초기 로딩 timeout과 서비스 응답 성능 목표를 구분합니다. 긴 제한 시간 자체를 성능 개선이라고 보고하지 않습니다.
- 관련 파일: [UI 테스트](../demo-ui/tests/test_ui.py).

## TS-005 — 문서 검사의 탐색 범위 정리

- 배경: 실제 의존성을 설치한 후 저장소 안에 .venv·빌드 산출물·작업 캐시가 추가되었습니다.
- 위험: 단순 재귀 탐색은 외부 라이브러리의 문서까지 검사할 수 있습니다. 이 문제로 링크 검사 실패가 실제 발생했다고 주장하는 것은 아닙니다.
- 조치: 숨김/캐시/빌드 폴더를 제외하고 프로젝트 문서만 탐색하도록 변경했습니다.
- 검증: 프로젝트 문서 링크와 합성 자료 검사가 통과했습니다.
- 관련 파일: [문서 검사](../scripts/check_docs.py).

## TS-006 — M1에서 RAG 준비 완료로 오해하지 않도록 상태 구분

## TS-007 — 테스트 의존성의 사용 중단 예정 경고

- 조치: 경고를 숨기지 않고 기록합니다. 의존성은 uv.lock에 고정되어 있습니다.
- 다음 확인: 후속 버전 갱신 시 TestClient 권장 클라이언트 전환을 검토하고 기존 인증·실패 처리 테스트를 다시 실행합니다.
- 완료 조건: 지원되는 조합으로 전환하고 동일 검증이 통과하며 해당 경고가 사라졌을 때 해결로 변경합니다.

## TS-009 — M2 실행 권한과 패키지 설치 차단

- 날짜/단계: 2026-09-05, M2.
- 증상: Docker 엔진 접근은 permission denied, PyPI 배포 정보 요청은 소켓 접근 거절로 실패했습니다. Docker 권한 확대 요청도 현재 sandbox_approval=false 정책으로 자동 거절됐습니다.
- 확인: 프로젝트 환경에는 torch, sentence_transformers, chromadb, langgraph가 설치되어 있지 않습니다. M1에서의 실행 허용과 현재 권한 정책은 달라졌습니다.
- 조치: 코드와 대체 객체를 사용하는 테스트를 작성하고, 실제 라이브러리·모델 검증은 별도 절차로 남겼습니다. M1 uv.lock과 기본 실행 구성을 유지하고 M2는 선택적 추가 구성으로 분리했습니다.
- 검증: 기존/신규 Python 37건, 정적·문법 검사는 통과했습니다. 실제 모델·LangGraph 실행은 아직 검증하지 못했습니다.
- 다음 작업: 허용된 실행 환경에서 추가 lock 생성 → 설치 → 실제 그래프 검사 → 모델 적재 → 통합 smoke.
- 상태: 미해결. 실제 M2 실행을 막는 외부 조건입니다.

## TS-010 — chunk 겹침 검사와 공백 정규화

- 증상: 분할 테스트에서 두 chunk의 문자 수 기준 겹침 비교가 실패했습니다.
- 원인: chunk 양끝 공백을 제거하는 정규화 때문에 token overlap과 최종 출력 문자열의 정확한 문자 길이가 같지 않았습니다. 실제 BGE tokenizer가 아닌 문자 tokenizer 대체 테스트에서 확인한 문제입니다.
- 조치: 연속 chunk에 필요한 문구인 “확인하고”가 양쪽에 남아 있는지 검사하도록 바꿨습니다. 모델 tokenizer의 실제 분할 검증은 후속 실제 적재 단계에 남깁니다.
- 검증: 해당 테스트 및 전체 Python 37건 통과.
- 상태: 단위 테스트 수정 완료, 실제 tokenizer 검증 대기.

### TS-009 재확인
사용자의 진행 요청 후 기본 실행 환경에서 다시 확인했습니다. Docker 엔진 파이프와 설정 파일 접근이 거절됐고, pypi.org:443 연결도 소켓 권한 오류로 실패했습니다. 현재 실행 정책은 바뀌지 않았으며 설치·실제 모델 검증은 시작하지 못했습니다.

### TS-009 권한 승인 후 재개 (2026-09-05)

- 기본 권한에서는 Docker 설정/파이프 접근 및 uv 캐시 초기화가 실패했습니다. 권한 확대 승인 후 Docker Engine 29.2.1 연결과 PyPI 의존성 해석·설치에 성공했습니다. 이전 차단 기록은 당시 결과입니다.
- M1 제약을 유지하여 M2 해시 lock을 생성했습니다. 기본 PyTorch 해석은 Linux CUDA 의존성을 포함하므로 CPU 배포로 다시 잠갔습니다.
- CPU 저장소를 전체 패키지의 우선 index로 지정한 시도는 certifi 버전 충돌로 실패했습니다. uv의 `--torch-backend cpu`로 PyTorch에만 저장소를 적용하여 해결했습니다. 설치 시에도 같은 옵션이 필요하며 Dockerfile에 반영했습니다.
- Windows 가상환경에 torch 2.14.0+cpu 및 M2 의존성을 설치했습니다. 실제 LangGraph 테스트는 2건 통과했습니다. pytest 기본 캐시 디렉터리 접근 경고가 있어 재검사에는 프로젝트 work 아래 캐시를 지정합니다.
- Docker 메모리 한도는 3,980,619,776바이트입니다. 모델 적재와 통합 검증은 진행 중이며 M2 완료를 의미하지 않습니다.
- 추가 확인: Git 상태 조회가 프로젝트 전용 저장소가 아닌 상위 저장소까지 탐색했습니다. 이후 Git 변경·커밋은 수행하지 않고 파일 단위로 작업합니다.


## TS-012 — 빌드 이력 출력 실패와 한도 중단

- 근거: 사용자가 전달한 CLI 출력. ingest/ai Built 이후 buildx history의 사용자 지정 출력에서 .ID 필드 해석 오류가 발생했습니다.
- 원인: 해당 실행 환경의 이력 출력 객체에 지정한 ID 필드가 없습니다. 이미지 빌드 자체의 실패로 해석하지 않습니다.
- 후속 조치: 기본 docker buildx history ls 및 Compose 이미지/컨테이너 상태로 확인합니다. 이번 정리에서는 Docker 조회를 재실행하지 않았습니다.
- 상태: 사용량 한도 종료로 최종 저장 응답 미확인. docs/progress-2026-09-05.md에 파일과 사용자 로그를 근거로 인계 기록을 별도 저장했습니다.

## TS-013 — 프로젝트 전용 Git 저장소 누락

- 확인: 프로젝트 .git 없음, git rev-parse --show-toplevel 결과는 상위 드라이브 루트입니다.
- 조치: 상위 저장소는 변경하지 않았습니다. GitHub 업로드 전에 프로젝트 독립 저장소 초기화와 범위 확인 절차를 인계 문서에 기록했습니다.
- 상태: 프로젝트 초기화·커밋·GitHub 업로드 미실행. 잘못된 범위에서 git add를 실행하지 않습니다.

### TS-013 프로젝트 저장소 분리 완료

- 프로젝트 폴더에서 git init -b main을 실행했습니다. 이후 git rev-parse --show-toplevel이 프로젝트 폴더를 가리키는 것을 확인했습니다.
- 상위 드라이브 저장소는 변경하지 않았습니다. 공개 GitHub 저장소 enterprise-ai-agent를 만들기로 사용자가 선택했습니다. 원격 생성/업로드는 인증 후 별도로 확인합니다.
