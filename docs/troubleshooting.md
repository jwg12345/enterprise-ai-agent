# 개선·문제 해결 기록

## M4 실제 커밋 후 응답 유실 검사 준비

성공 응답을 단순 재전송하는 검사만으로는 커밋 후 응답 유실을 검증할 수 없어 검사 전용 HTTP transport를 작성했습니다. 실제 Spring 응답 본문을 받은 시점에 티켓 ID·멱등 키를 증거로 저장하고 런타임에는 ReadError를 전달합니다. 실행 checkpoint가 execute에 남는지 확인한 뒤 별도 일회성 프로세스에서 재개하고 별도 관리용 읽기 쿼리로 티켓/생성 감사 개수를 확인합니다. 운영 서비스에 장애 주입 설정을 추가하지 않았고 AI 계정의 business 접근 제한도 유지합니다.

신규 검사 4개와 기존 실행 API 16개 합계 20 passed, 경고 1개 및 Ruff 통과. 앱의 실제 실행 시도는 Docker 사전 확인 실패로 종료되어 합성 티켓을 만들지 않았습니다. 실제 PostgreSQL 결과는 사용자 실행 대기입니다. 기존 migration 파일명 추정 조회는 실패했으며 파일 목록에서 V2__approval_ledger.sql을 찾아 UUID/감사 스키마를 확인했습니다. [검사 범위·실행·재개 절차](m4-response-loss.md)에 중단 시 기존 키를 보존하는 규칙을 기록했습니다.

## 2026-09-07 새 질문 평가의 504 이후 503과 진단 보완

- 새 합성 질문 8건의 실제 평가에서 첫 요청 504, 이후 7건 503을 관측했습니다. 응답 본문 오류는 기존 평가기가 저장하지 않아 내부 세부 원인을 확정하지 않습니다. 성공은 0/8이며 의미 품질은 미판정입니다. 추가 호출을 중단했습니다.
- 코드 확인: asyncio timeout은 실행 중인 임베딩 thread를 강제로 종료하지 않습니다. RagStore의 잠금은 그 작업이 끝날 때 해제되므로 후속 검색이 거절될 수 있습니다. 관측과 일치하는 가설이며 실제 자원 계측 없이 확정하지 않습니다. 잠금을 제거하거나 timeout만 늘려 오류를 숨기지 않았습니다.
- 평가기 개선: client_timeout/connection_error/invalid_json/http_error를 구분하고 검색 steps를 저장합니다. 클라이언트 65초로 서버 60초 오류 응답을 관측하도록 했습니다. 서버 5xx에도 계속 질의하던 평가기를 첫 실패 후 중단하고 계획 분모를 유지하도록 수정했습니다.
- 읽기 전용 진단 스크립트는 health와 해당 Compose 컨테이너의 CPU·메모리·OOM 여부만 수집합니다. .env, 원문 로그, LLM API를 읽거나 호출하지 않습니다. 앱 실행 결과는 live/ready 200이나 Docker 접근 실패여서 자원 데이터가 없습니다. 사용자 PowerShell에서 수집해야 합니다.
- 모의 장애 주입 테스트 첫 실행은 대체 runtime에 close 메서드가 없어 종료 시 3건 실패했습니다(74 passed). 테스트 대역에 비동기 close를 추가했고 재실행 77 passed, 경고 1개였습니다. 서비스 코드 오류로 오인하지 않았습니다. 실제 장애 결과와 모의 검사 결과를 구분해 [M4 현황](m4-status.md)에 기록했습니다.

## 빈 보류 문구로 발생한 502 수정

호스트 통제 재현에서 제공자는 세 합성 질문 모두 HTTP 200과 abstain=true를 반환했지만 answer가 빈 문자열이어서 최소 1자 스키마 검증에 실패했습니다. 네트워크 접근이 처음 거부돼 연결 확인이 안 됐고 권한 승인 후 응답 형식만 출력해 원인을 확인했습니다. 실제 서비스의 검색 근거 전체와 동일하다고 단정하지는 않습니다.

명시적인 빈 보류 문구만 안내 문장으로 정규화하고, 인용 검증은 먼저 수행하도록 수정했습니다. false 보류·null·누락·잘못된 출처·제공자 오류는 계속 실패합니다. 프롬프트에도 보류 사유를 요청하고 버전 m2-v2를 기록합니다. 관련 35개 테스트 통과, 실제 제공자+수정 호스트 Adapter 3건 모두 정상 보류 확인. 실행 컨테이너 적용 후 API 재검증은 남아 있습니다. 모델 응답 오류를 임의 답변 성공으로 바꾼 수정이 아닙니다.

- 최초 ingest에서 공개 BGE-M3 캐시 약 2.2GiB 및 가중치 로딩을 확인했지만 활성 manifest 생성 전 지연됐습니다. 프로세스 관측 VmSwap 429,096kB, VmHWM 2,639,184kB, Threads 31이었고 OOMKilled=false였습니다. 스왑은 확인된 사실이며 지연의 유일한 원인으로 단정하지 않습니다. 로그만으로 모델 준비와 문서 인코딩의 정확한 단계별 시간을 분리하지 못했습니다.
- 현재 적재 컨테이너만 중지하고 캐시·DB·Chroma volume은 보존했습니다. stop --time은 deprecated 경고가 있어 이후 --timeout을 사용합니다.
- compose.m2.yaml의 AI/ingest에 OMP_NUM_THREADS=2, MKL_NUM_THREADS=2를 설정했습니다. 기존 캐시를 사용하는 HF_HUB_OFFLINE=1 적재 재시도를 시작했습니다. 실제 모델을 대체하지 않으며 캐시 누락이면 오류로 중단합니다.
- 기존 get_sentence_embedding_dimension의 이름 변경 FutureWarning도 관측했습니다. 실제 차원 검사 실패는 아니며 경고를 숨기지 않습니다.
- 브라우저 도구는 연결된 브라우저가 없음을 반환했습니다. scripts/smoke_m2_ui.py로 실제 API를 쓰는 Streamlit 화면 요소 검사를 준비했고 브라우저 시각 검증과 구분합니다.

### TS-015 최종 검증 결과

CPU 스레드 2개와 기존 모델 오프라인 캐시를 사용한 ingest는 `Ingested 4 chunks into manuals-c567565b8404-41987ec1` 출력 후 종료 코드 0으로 성공했습니다. M2 기동과 seed도 종료 코드 0, 실제 검색 smoke와 실제 API를 사용하는 Streamlit AppTest 화면 요소 검사가 모두 통과했습니다. mode=extractive이며 생성형 LLM 검증은 아닙니다. 최초 실행과 재시도의 캐시·부하 조건이 달라 CPU 설정만의 성능 효과로 단정하지 않습니다.

브라우저 미연결로 픽셀/레이아웃 검증은 미실시입니다. Streamlit use_container_width 사용 중단 예정 경고와 Sentence Transformers 메서드 이름 변경 경고가 남았습니다. 문서 수정 시 일부 patch 문맥이 일치하지 않아 실패했고 실제 파일을 읽어 필요한 부분을 다시 반영했습니다. Git diff의 저장소 미인식은 해당 실행에서 관측했으며 저장소 삭제·재초기화·업로드는 수행하지 않았습니다. 검증 명령·검색 거리 관측·재개 순서는 [M2 현황](m2-status.md)에 저장했습니다.

## LLM 모드 설정 누락 재확인

AI Healthy 후 실제 질문은 HTTP 200이지만 mode=extractive였습니다. 로컬 환경 파일의 정확한 LLM_MODE 항목이 없는 것을 확인했습니다. 누락 경위는 확정하지 않았습니다. 기존 치환만 수행하면 항목이 없을 때 추가되지 않는 한계가 있어, 항목이 없으면 추가하고 있으면 교체하는 방식으로 compatible 설정을 저장하고 재확인했습니다. 컨테이너 재생성 후 mode=compatible 재검증이 필요합니다. 별도 화면의 오류 응답 원인은 이 확인만으로 확정하지 않습니다.

### LLM 모드 누락 해결 검증

아래 기록 이후 2026-09-06 앱 재개에서는 Docker 접근이 다시 거부됐고 localhost:8000은 연결 거부였습니다. 서비스 중지 여부 자체는 Docker에서 확인할 수 없었습니다. uv 캐시는 프로젝트 work/uv-cache로 지정해 실행했지만 전체 pytest는 orjson DLL 접근 거부로 수집 실패했습니다. DLL 차단의 상세 원인은 미확정이며 패키지를 삭제하거나 재설치하지 않았습니다. 평가 실행기 4건·UI 2건은 별도로 통과했고 ruff·문서 검사도 통과했습니다. Streamlit 너비 옵션 경고는 width="stretch"로 수정했습니다. 평가기의 응답만으로 DB 쓰기 0건을 추정하던 검사를 제거하고 인용·도구 검증 및 중단 시 분모 보존을 추가했습니다. 실서비스 평가는 권한 있는 CLI에서 재개해야 하며 명령은 [최신 M2 현황](m2-status.md)에 기록했습니다.

누락된 LLM_MODE를 compatible로 추가하고 사용자가 AI 컨테이너를 재생성한 뒤 실제 API가 HTTP 200과 mode=compatible 및 근거 기반 한국어 답변을 반환했습니다. 설정 누락 문제의 해결을 확인했습니다. 키 값은 기록하지 않았습니다.
