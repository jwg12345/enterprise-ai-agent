# 프로젝트 경험 정리

AI 코딩 도구를 활용해 구현하고 검증한 프로젝트의 설계 판단과 문제 해결 과정을 정리합니다. 합성 데이터를 사용한 로컬 시연 프로젝트이며, 실제 기업 도입이나 업무 시간 절감 효과는 측정하지 않았습니다.

## 한 문장 소개

운영 매뉴얼과 장애 기록으로 후속 티켓 초안을 제안하고, 사람 승인과 서버 검증을 거쳐 저장하는 업무 대응 AI Agent를 AI 코딩 도구와 함께 구현·검증했습니다.

## 대표 경험 1 — 생성형 AI와 업무 쓰기 권한 분리

문제: AI가 만든 답변을 바로 업무 변경으로 연결하면 승인 여부나 권한을 신뢰하기 어렵습니다.

설계: FastAPI/LangGraph는 초안·실행 흐름을 담당하고, Spring이 승인 소유권·초안 해시·만료·티켓 저장을 검증하도록 경계를 나눴습니다. AI 계정은 business 스키마에 접근하지 못하도록 분리했습니다.

근거: 승인 전 쓰기 차단, 거절·권한·멱등성 검사와 실제 승인 후 티켓 생성 시연. 승인 여부는 LLM 출력이 아닌 서버 원장을 기준으로 판단합니다.

## 대표 경험 2 — 응답 유실에서도 중복 생성 방지

문제: 서버 저장은 성공했는데 응답을 받지 못하면 재시도 시 중복 티켓이 생길 수 있습니다.

접근: 대기 노드와 쓰기 노드를 분리하고 PostgreSQL 체크포인트를 사용했습니다. 승인 원장과 같은 멱등 키로 결과를 재확인하도록 구성했습니다.

검증: 실제 Spring 커밋 응답을 검사 transport에서 버리고 별도 프로세스로 재개했습니다. 최종 티켓과 생성 감사 기록이 각각 1건임을 DB로 확인했습니다. 검증 범위는 테스트 계층의 응답 유실 주입과 별도 프로세스 복구이며, 실제 네트워크 단절 실험은 포함하지 않습니다.

## 대표 경험 3 — 추측 대신 단계별 관측으로 지연 분석

문제: 로컬 질문이 60초 제한을 넘겼고 이후 검색 불가 응답이 발생했습니다.

접근: 컨테이너/호스트 메모리·CPU를 함께 확인하고 검색 단계를 나눠 시간을 기록했습니다. 질문 임베딩 41.6초, 벡터 검색 0.184초로 지연 구간을 좁혔고 기동 워밍업을 추가했습니다.

한계: 이후 8건은 모두 정상 응답했지만 비교 조건을 통제하지 않았으므로 성능 개선율은 주장하지 않습니다. 측정 결과만으로 메모리 부족을 단일 원인으로 확정하지 않았습니다.
