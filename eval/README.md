# 평가 준비 자료

## M2 검색 품질 기준선

### 임계값 적용 전 거리 수집

권한 있는 프로젝트 PowerShell에서 `uv run --no-sync python scripts/calibrate_rag.py`를 실행합니다. 기존 Docker 이미지·모델 캐시·인덱스와 실행 중인 Chroma가 필요합니다. 측정 중 AI를 잠시 중지하고 종료 시 기존 컨테이너를 다시 시작해 Healthy를 기다립니다. 두 모델의 동시 메모리 점유를 피하기 위한 조치입니다. 측정 동안 화면 요청은 실패할 수 있습니다. 강제 종료 시 `docker compose -f compose.yaml -f compose.m2.yaml --profile rag start --wait --wait-timeout 300 ai`로 복구합니다.

별도 ingest 컨테이너에서 적재 대신 읽기 평가 코드를 실행합니다. viewer 권한 필터는 유지하며 개발셋 10건의 top 5 후보를 거리 2.0까지 수집합니다. 모델/인덱스를 새로 만들거나 OpenAI를 호출하지 않습니다. 고정셋은 읽지 않습니다. 결과는 `eval/results/rag-calibration-<실행시각>.json`에 저장합니다.

정답 섹션을 모두 검색하면서 근거 없는 질문에 후보를 반환하지 않는 개발 임계값이 있는지 검사합니다. 가능하면 기준 0.45에 가장 가까운 후보를 제안하고, 불가능하면 recommended=null로 기록합니다. 제안은 자동 적용하지 않으며 거리만으로 해결되지 않는 경우 검색/답변 전략을 재검토합니다. 이 보수적 기준에서 주변 문서 검색은 false retrieval로 계산되지만 LLM의 올바른 보류 여부와는 별도입니다. 모델 revision·인덱스 manifest·데이터셋 해시를 함께 저장합니다. 실제 Docker 측정은 아직 검증 전입니다.

- `rag-dev.jsonl`: 개발 질문 10건(답변 가능 6건, 근거 없음 4건). 기준 조정과 실패 분석에 사용합니다.
- `rag-fixed.jsonl`: 별도 확인 질문 30건(답변 가능 18건, 근거 없음 12건). 개발 단계에서는 실행하지 않고 기준을 고정한 뒤 한 번 평가합니다. 결과를 보고 이 셋에 맞춰 조정하면 더 이상 독립 평가로 보고하지 않습니다.
- 두 셋은 합성 매뉴얼 2개를 대상으로 사람이 읽을 수 있는 질문을 작성한 소규모 자료입니다. 표현과 주제가 유사해 완전한 일반화 평가가 아니며 자연어 업무 조회·승인 실행 평가는 포함하지 않습니다.

`uv run --no-sync python scripts/evaluate_m2.py --split dev`로 개발셋을 실행합니다. 기준 고정 후 `--split fixed`를 사용합니다. 결과는 `m2-rag-dev-*.json` / `m2-rag-fixed-*.json`으로 분리해 초기 smoke 보고서를 덮어쓰지 않습니다. compatible 모드에서는 실제 LLM 호출 비용이 발생합니다.

문서 ID뿐 아니라 정답 섹션 존재도 확인합니다. 근거가 없는 질문은 보류 여부를 검사하며 주변 주제의 검색 출처가 남아 있다는 이유만으로 실패시키지 않습니다. 초기 smoke의 빈 출처 검사는 유지합니다. 반환된 거리·인덱스 ID를 기록하지만 임계값 밖에서 버려진 검색 결과는 관측하지 못하므로 이 API 평가만으로 임계값을 자동 보정하지 않습니다. 답변 주장 충실도는 별도 사람 검토가 필요합니다.

최초 개발 실행(20260905T224745Z): 9/10 통과. `rag-dev-02`는 답변 가능한 Gateway 다음 점검 대상 질문인데 검색 결과가 비어 보류했습니다. 관련 질문 5/6, 근거 없음 질문 4/4 계약 검사 통과. 이 결과는 검색 임계값 보정 완료나 일반 정확도 90%를 의미하지 않습니다. 고정셋은 아직 미실행입니다.

`dataset.jsonl`은 실행기 개발용 초기 사례 8건이며 평가 완료 결과가 아닙니다. 각 행의 id는 고유하고 expected_sources는 원본 문서의 document_id를 참조합니다.

expected_tools는 해당 사례 전체 실행에서 허용/기대되는 도구 집합입니다. decision이 없는 조회 사례는 쓰기를 수행하지 않습니다. 상태를 넣은 사례는 실행기가 해당 승인 조건을 준비해야 하며 query만으로 만료·경합 테스트를 대체할 수 없습니다.

M4에서 개발셋과 고정 평가셋을 분리하고 실제 검색·Agent 실행기로 측정합니다. 안전성 사례는 pytest/JUnit의 DB 변경 건수 assertion으로도 검증합니다. 결과 규격은 [운영 문서](../docs/operations.md)를 따릅니다.

M2에서는 먼저 `scripts/evaluate_m2.py`로 현재 서비스가 처리할 수 있는 `rag-*`와 `guard-01` 사례만 실행합니다. 이 스크립트는 live API에 요청하고 `eval/results/m2-latest.json`과 timestamp가 포함된 결과 파일을 남깁니다. 서비스가 꺼져 있거나 아직 M2 준비 상태가 아니면 실패 결과를 저장하고, 이를 통과로 기록하지 않습니다.

저장소 루트에서 `uv run --no-sync python scripts/evaluate_m2.py`로 실행합니다. compatible 모드에서는 실제 LLM 호출 비용이 발생합니다. .env의 데모 인증 토큰을 사용하며 비밀 값과 원문 답변은 보고서에 저장하지 않습니다. CI는 extractive 모드로 실행하고 결과를 artifact로 보관합니다.

초기 3건의 계약 검사이며 일반 검색 품질 점수가 아닙니다. 문서 ID, 인용 chunk ID, 도구 집합, 보류/거절 여부를 확인합니다. DB 쓰기 건수와 답변 주장 충실도는 검증하지 않습니다. 실제 서버 모델·인덱스 버전 확인, 개발셋/고정 평가셋 분리, 관련성 임계값 보정은 남아 있습니다. 중간 연결 실패 시 전체 예정 건수와 완료 건수를 따로 기록합니다.
